Where dialects differ

The same SQL text can read differently from one database to the next. The common dialect handles these for you, and each database’s own template, for SQL outside it, checks them with that database’s rules. Three places it matters, with examples from Wherewith's tests:

Backslashes in strings

MySQL and MariaDB read \ in a string as an escape, unless NO_BACKSLASH_ESCAPES is on. SQLite, DuckDB, and PostgreSQL (with standard_conforming_strings on, its default) read it as text.

If ignored, a string quoted the standard way can go on past its closing quote in MySQL, since \' is a quote inside the string.

Wherewith escapes backslashes only in the mysql profile, and refuses a MySQL template whose strings the two modes would end in different places. A common query refuses \ in its strings while MySQL is a target: bind that text as a value instead.

Long or odd names

PostgreSQL cuts names down to 63 bytes, without an error. MySQL and MariaDB reject names over 64 characters, and names ending in whitespace.

If ignored, two long PostgreSQL names that differ only after 63 bytes name the same table.

Wherewith refuses such names up front, for each profile. An Identifier, and every name in a common query, must suit them all.

Nested comments

PostgreSQL and DuckDB nest /* */ comments, and SQLite and MySQL don't, so /* /* */ is a whole comment to SQLite and MySQL, and still open to PostgreSQL and DuckDB.

If ignored, a placeholder that looks like code can be inside a comment, where the database never sees it.

Wherewith reads each template the way its database does, and refuses a hole that would land in a comment. A common query refuses /* inside a comment, and never writes comments out.

Why Wherewith

  • Written once, for every database. The common dialect is SQL each database reads the same way. What would differ is written the way each one needs, or refused, with its line and column, when the query is built.
  • Values become placeholders. A template's values go to the driver as parameters, with their types, so a value never becomes SQL, whatever it holds.
  • Names are quoted for the dialect. "students" for PostgreSQL, `students` for MySQL, with each database's own limits. A name that can't be written safely, such as a 64-byte PostgreSQL name, is refused, not cut short.
  • Mistakes are refused, not guessed at. A value inside quotes or a comment, a stray ? or $1 in the text, or text that ends inside a quote: Wherewith says what's wrong instead of building the query.
  • Each database’s own SQL, too. For SQL outside the common dialect, templates for SQLite, PostgreSQL, MySQL and MariaDB, and DuckDB check it with that database's rules. Every query renders with whichever placeholder style the driver takes: .
  • Tested against real engines. Its tests run in all seven languages, and round trips run hostile input and random templates through SQLite, DuckDB, PostgreSQL 18, and MariaDB 11.8, checking that quoted strings and names read back exactly, bound values come back equal, and common queries give the same rows on each.
